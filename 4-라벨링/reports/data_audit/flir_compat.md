# D — `pilot/flir.py` 라디오메트릭 호환성 확인

## 날짜
2026-08-28

## 범위

**확인만 했다.** `pilot/flir.py` 를 수정하지 않았고 파이프라인에 편입하지도 않았다.
pilot 은 읽기 전용이다. 원본 이미지도 열기만 했다.

## 방법

반 × 카메라 30개 층마다 10장씩, 표본 **300장**에 `flir.read()` 를 돌렸다.
seed 20260828 고정.

## 결과 — 코드는 정상 동작한다. 문제는 데이터 쪽이다

| 판정 | 건수 |
|---|---:|
| OK | 100 |
| FAIL | 200 |

성공한 100장은 전부 동일했다.

| 항목 | 값 |
|---|---|
| 열화상 해상도 | 320×240 (100/100) |
| 내장 실화상 | 640×480 (100/100) |
| 카메라 모델 | FLIR E8 (100/100) |
| 온도 범위 | 17.7 ~ 96.7 °C |

**`pilot/flir.py` 는 수정 없이 현재 데이터에 그대로 동작한다.**

## 핵심 발견 — 라디오메트릭 데이터는 카메라별로 갈린다

| 카메라 | 표본 OK | 표본 FAIL | 판정 |
|---|---:|---:|---|
| IR1 | 100 | 0 | **APP1 있음 · 온도 추출 가능** |
| IR2 | 0 | 100 | APP1 없음 |
| IR3 | 0 | 100 | APP1 없음 |

실패 사유 199건이 `FLIR APP1 세그먼트 없음 (방사 데이터 미포함 파일)` 이다.
나머지 1건은 `KeyError: 42` (Real2IR 레코드 부재) — `P7-VCB&CT반/A3_B1_P7_2022-07-01_IR2_00008.jpg`.
이것도 IR2 다.

전수 데이터의 카메라 구성:

| 카메라 | 이미지 | 비율 | 온도 추출 |
|---|---:|---:|---|
| IR1 | 2,512 | **2.4%** | 가능 |
| IR2 | 54,686 | 51.3% | 불가 |
| IR3 | 49,487 | 46.4% | 불가 |
| 합계 | 106,685 | 100% | |

> **전체 이미지의 2.4% 만 온도 값을 갖는다.**
> 온도를 입력으로 쓰는 접근은 나머지 97.6% 에는 적용할 수 없다.

표본이 층마다 10장이므로 "IR2·IR3 에 라디오메트릭이 **전혀** 없다"고 단정하지는
않는다. 층 30개 × 10장에서 예외가 0건이었다는 것까지가 확인된 사실이다.
전수 확인은 하지 않았다.

## 함께 확인된 사실 — 정본 라벨 1,036장은 전부 IR1 이다

| | IR1 | IR2 | IR3 |
|---|---:|---:|---:|
| 정본 라벨 이미지 | **1,036** | 0 | 0 |

이 사실은 앞선 두 작업의 해석을 바로잡는다.

- **B(OSD) 정정**: "OSD 면적 5% 초과 49박스가 전부 IR1" 을 카메라 특성으로 적어
  두었으나(`원인 UNKNOWN`), 원인은 자명하다 — **정본 라벨 자체가 전부 IR1** 이다.
  카메라별 OSD 차이의 증거가 아니다. IR2·IR3 의 OSD 중첩은 라벨이 없어 측정하지 못했다.
- **C(분할) 함의**: 라벨은 전부 IR1 이므로, 카메라 층화가 유지되어도 실제 라벨의
  train/val/test 배분은 IR1 층 하나로 결정된다.

C 에서 만든 잠정 분할에서 정본 라벨 1,036장의 배분:

| split | 이미지 | 비율 | 대표 |
|---|---:|---:|---:|
| train | 723 | 69.8% | 681 |
| val | 155 | 15.0% | 146 |
| test | 158 | 15.3% | 146 |

목표 70/15/15 에 근접한다.

## 결정하지 않은 것

- 온도 값을 모델 입력으로 쓸 것인가 (2.4% 에서만 가능)
- IR2·IR3 를 온도 없이 쓸 것인가, 별도 도메인으로 볼 것인가
- `flir.py` 를 4-라벨링 파이프라인에 편입할 것인가

→ OQ-017 로 남긴다.
