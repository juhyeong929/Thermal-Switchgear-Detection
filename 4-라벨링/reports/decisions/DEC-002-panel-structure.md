# DEC-002 — 반(Panel)을 독립 데이터 도메인으로 유지, 원본은 이동하지 않음

## 날짜
2026-08-27

## 결정 내용
0. **작업 범위는 현존 10개 반이다.** P11~P13 은 원본 zip 잔존 여부와 복구 필요성을
   별도 결정사항(DEC-006)으로 관리하며, 복구하기 전까지 라벨링 범위에 포함하지 않는다.
1. `3-가공` 의 반 폴더를 **병합하지 않는다.** 각 반은 독립 데이터 도메인이다.
2. 반(Panel) = "이 데이터가 어디서 수집되었는가", 클래스(Class) = "이 안에서 무엇을
   라벨링하는가". 두 개념을 분리해 관리한다. 클래스만 공통 28개로 통일한다.
3. 원본 이미지를 `4-라벨링` 으로 복사·이동하지 않는다. `schemas/paths.py` 에서 경로만
   참조하고, 작업 산출물만 `4-라벨링/data` 아래에 쌓는다.

## 문제
가이드 `02 PANELS` 는 8개 반만 상세를 두는데 실제 데이터 폴더는 10개다.
P3-MOF반 · P8-ACB반 · P9-MCCB반 은 가이드에 단독 상세가 없다.
이들을 가이드의 8개 반에 흡수시키면 폴더가 정리되는 대신, 수집 출처 정보가 사라진다.

## 검토한 선택지
1. **가이드 8개 반에 흡수** — P3→MOF&PT, P8·P9→ACB&MCCB. 가이드와 1:1이 되지만
   서로 다른 설비에서 찍은 데이터가 섞이고, 나중에 반별 성능 편차를 볼 수 없다.
2. **현존 10개 폴더를 그대로 유지** ← 선택
3. 새 반을 만들어 가이드를 확장 — 가이드는 이번 범위에서 손대지 않기로 함

## 선택한 이유
반 구조는 촬영 현장의 사실이고, 클래스는 라벨링 규칙이다. 사실을 규칙에 맞추려고
지우면 복구할 수 없다. 반대로 반을 유지한 채 클래스만 공통화하면 둘 다 보존된다.
데이터 누수 방지(같은 반이 train/val 에 갈리지 않게)와 반별 성능 편차 보고도
반 정보가 살아 있어야 가능하다.

원본 미이동은 별개 이유다. 이미지가 106,685장이라 복사하면 디스크가 두 배로 들고,
원본과 사본 중 어느 쪽이 기준인지 흐려진다.

## 근거
- 실측 `reports/data_audit/panel_inventory.csv` — 반별 이미지 수·촬영 세션 수·카메라 분포
- 반마다 촬영 세션(site·building·date·camera 조합)이 7~37개로 다르다.
  같은 반 안에서도 회차가 갈리므로 반을 합치면 이 층위가 한 번 더 뭉개진다

## 영향

  `PANEL_CLASSES_PROVISIONAL` 로 **잠정** 표시했고, 확정은 OPEN QUESTION 으로 남긴다
- P8-ACB반은 현재 라벨 가능 클래스가 0종이다 (OQ-002)
