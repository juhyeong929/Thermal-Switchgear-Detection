## 왜 바뀌는가

개정 PDF p18 (ACB&MCCB 반) 이 가공대상 목록에 넣었다.

```
p18   콘덴서 · MCCB · ACB 접촉부 · MCCB 접촉부
이전 판 03 REFERENCE   27 ACB 접촉부  X  "배전반 내 위치때문에 잘 안보임"
```

`인입선로 접촉부`(DEC-027)와 **완전히 같은 증거 구조**다 — 이전 판은 제외/보류,
개정 판은 가공대상 목록에 포함, 가공여부 기호 체계 자체는 사라졌다.
같은 근거 자료를 한쪽만 받아들이지 않는다.

## 왜 '가공' 이 아니라 '주의' 인가

비고 원문이 `"배전반 내 위치때문에 잘 안보임"` 이고, **같은 문구를 가진 클래스가
가이드 안에서 이미 주의로 대응돼 왔다.**

| # | 클래스 | 비고 | 이전 판 등급 |
|---:|---|---|---|
| 1 | 철심부 | 배전반 내 위치때문에 잘 안보임 | **주의** |
| 26 | CT 접촉부 | 배전반 내 위치때문에 잘 안보임 | **주의** |
| 27 | ACB 접촉부 | 배전반 내 위치때문에 잘 안보임 | 제외 |

세 클래스의 사유가 같은데 하나만 제외였다. 개정 판이 그 하나를 가공대상으로 올렸으므로
**나머지 둘과 같은 자리**로 보내는 것이 가이드 내부 논리와 맞는다. 없던 등급을 새로
만들거나 사유가 같은 클래스를 서로 다르게 두지 않는다.

`주의` 의 뜻은 "식별 가능할 때만 라벨, 판별 불가면 미라벨/Ignore" 이고,
"잘 안 보인다" 는 사유와 그대로 맞물린다.

## 승격과 단위 확정을 분리한다 — 여기서 실제로 사고가 났다

`label_status` 만 바꾸고 `ANNOTATION_UNIT` 에 적지 않았더니 **바로 배포 대상이 됐다.**

```
annotation_unit()  ANNOTATION_UNIT 에 없으면 기본값 WHOLE_OBJECT 를 준다
                   -> unit_confirmed() = True
                   -> deployable() 통과
                   -> 라벨 실적 0건인 클래스가 라벨러 화면에 실린다
```

`branch_contact` 폐지 때와 **같은 함정**이다. 그때는 라벨 대상이 아닌 클래스가 새는
경로였고(`NOT_LABELED` 면 UNKNOWN 을 돌려주도록 고쳤다), 이번은 **라벨 대상이지만
근거가 없는 접촉부**가 자동으로 확정되는 경로다.

두 가지로 막았다.

```
1. ANNOTATION_UNIT["acb_contact"] = UNIT_UNKNOWN 을 명시
2. status_check [2] 에 "접촉부 단위가 전부 명시됐는가" 검사 추가
     라벨 대상 중 이름이 '접촉부' 로 끝나는데 ANNOTATION_UNIT 에 없으면 FAIL
```

접촉부 계열은 **근거 없이 WHOLE_OBJECT 로 두지 않는다.** 부품 단위가 자명한
그 밖의 클래스와 다르다.

## 함께 확인한 것 — 바꾸지 않은 것들

| 항목 | 확인 결과 |
|---|---|
| CT 접촉부 | **이미 P7-VCB&CT반 후보에 있다.** 추가할 것이 없었다. 주의 · UNKNOWN · 비배포 유지 |
| `PT` (PDF p13 표기) | 정본 명칭 `몰드타입 PT` 유지. DEC-003 이 `PT -> 몰드타입 PT` 로 구체화한 개정이므로 축약 표기 때문에 되돌리지 않는다. `PT` 는 이미 alias 에 있다 |
| `VCB접촉부` · `ACB접촉부` (붙여쓰기) | 공백 있는 정본 명칭 유지. PDF 자체가 일관되지 않다(p15·p18 은 공백, p17 `CT접촉부` 는 붙여쓰기). 회수 도구가 공백 차이를 흡수한다 |

**원문 표기와 프로젝트 정본 명칭을 분리한다.** 원문이 축약·붙여쓰기로 적혀 있어도
정본은 하나로 두고, 들어오는 표기는 alias·공백 정규화로 받는다.
