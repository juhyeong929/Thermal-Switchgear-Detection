## 2. 가이드의 결정적 문구 — "명칭을 통일한다"

가이드 v2 원문 3곳:

> ⑤ VCB 반 — `CT·SA를 신규 가공대상으로 추가하고, **분기 접촉부는 케이블헤드로 명칭을 통일한다.**`
>
> ⑥ 교사교육센터 CNCV 반 — `**분기 접촉부를 케이블헤드로 명칭을 통일한다.**`
>
> 개정 내역 — `VCB 반에 **케이블헤드로 명칭을 통일**하고`, `교사교육센터 CNCV 반에 **케이블헤드로 명칭을 통일**`

파이프라인 문서도 같다.

> `14 케이블헤드 · 가공 · v1 "분기 접촉부" → **명칭 통일**`

가이드는 이 변경을 **범위 재정의가 아니라 명칭 통일**로 기술한다.
"대상을 바꾼다"거나 "범위를 좁힌다"는 표현은 어디에도 없다.

**주의할 구분**: LBS&LA 반의 케이블헤드는 다르다.
가이드는 `LBS&LA 반에 케이블헤드를 **추가**하고` 라고 쓴다. 이쪽은 신규 항목이다.
명칭 통일은 **VCB·CNCV 반에만** 해당한다.

## 3. 결정적 증거 — 가이드 자체의 예시 이미지

파이프라인 문서가 경계 판단의 1차 기준을 지정해 두었다.

> `항목별 정확한 박스 경계(포함/제외 픽셀 범위)는 **v2 가이드의 반별 상세 사진과 색상 스와치를 1차 기준**으로 삼는다`

그래서 가이드 HTML 에 base64 로 박혀 있던 이미지 19장을 추출해 확인했다
(`experiments/seed_selection/guide_images/`, 원본 HTML 은 수정하지 않음).

### `라벨링 예시 화면 · 케이블헤드` 2장 — CVAT 스크린샷

**두 장 모두 CVAT 객체 패널의 라벨명이 `분기 접촉부` 다.**

| 이미지 | 객체 | 라벨명 |
|---|---|---|
| 14번 (VCB 반) | RECTANGLE SHAPE 7 · 8 · 9 | **분기 접촉부** |
| 16번 (CNCV 반) | RECTANGLE SHAPE 4 · 5 · 6 | **분기 접촉부** |

가이드는 `케이블헤드` 라는 캡션을 달고 **`분기 접촉부` 로 라벨된 화면을 그대로 예시로 실었다.**
가이드 작성자 본인이 두 명칭을 같은 대상으로 다루고 있다는 직접 증거다.

### 그 박스가 잡은 범위

두 예시 모두 동일한 경계를 보인다.

```
포함:  상단 금속 단자·러그  ->  연결 도체  ->  리브(shed) 적층부 하단
제외:  그 아래로 이어지는 케이블
```

14번은 흰색 리브 콘 위의 금속 러그부터, 16번은 볼트가 박힌 상단 금속판부터 박스가 시작한다.
아래쪽 검은 케이블은 박스 밖이다.

## 5. 참고 라벨 387개는 실제로 무엇을 박스쳤는가

기존 bbox 를 정답으로 가정하지 않고 측정만 했다.

| 지표 | 값 |
|---|---:|
| 박스 높이 중앙 | **0.531** |
| 높이 ≥ 0.5 (프레임 절반 이상) | 254개 (66%) |
| 높이 ≤ 0.2 | 11개 (3%) |
| 종횡비 중앙 · IQR | 0.19 · 0.06 |

**Q1. 387개가 케이블헤드 전체를 라벨한 것인가** → 대체로 그렇다.
높이 중앙 0.531 은 리브 적층부만 잡기에는 너무 크다. 대표 사례 12건을 열어 보니
다수가 `상부 단자 + 도체 + 리브 적층부` 를 함께 감싸고 있었다. 가이드 예시와 같은 범위다.

**Q2. 단순히 분기 접촉 지점만 라벨한 것인가** → 아니다.
접촉 지점만 잡은 작은 박스는 11개(3%)뿐이고, 그것도 아래 Q3 의 이상치다.

**Q3. 두 유형이 혼재하는가** → **소수 혼재한다. 다만 성격이 다르다.**

| 유형 | 건수 | 성격 |
|---|---:|---|
| 상부 단자 포함 (다수 관행) | 대다수 | 가이드 예시와 일치 |
| 리브 적층부만 | 소수 | 실제 관행 차이 (case_03 왼쪽, 00044 왼쪽, 00048 왼쪽) |
| 초소형·가로형 이상치 | 11 (3%) | **케이블헤드 형태가 아니다.** 종횡비 0.78~1.85, 일부는 OSD 컬러바에 겹침 — 오라벨 의심 |

처음에 `상부 도체 제외 관행` 으로 뽑았던 3건(00054·00017·00021)을 열어 보니
케이블헤드가 아니라 **이상치 오라벨**이었다. 화면의 실제 애자들은 미라벨 상태였다.
즉 "제외 관행"의 상당 부분은 관행이 아니라 품질 문제다.

**Q4. 같은 세션·같은 구조에서 범위가 반복적으로 달라지는가** → **일부 그렇다.**
177장 중 41장(23%)에서 같은 프레임 안 등가 박스의 높이비가 1.25 이상이다.
등가 쌍 251개 기준으로는 ≥1.3 이 28개(11%), ≥1.5 가 5개(2%).

## 6. 가설 검증

### Hypothesis A — 구 `분기 접촉부` = v2 `케이블헤드` … **채택**

증거
- 가이드 v2 가 3곳에서 **"명칭을 통일한다"** 로 기술. 범위 변경 표현 없음
- 파이프라인 문서도 `v1 "분기 접촉부" → 명칭 통일`
- **가이드의 `케이블헤드` 예시 이미지 2장이 CVAT 에서 `분기 접촉부` 로 라벨되어 있다**
- 예시 박스의 범위와 참고 라벨 387건의 다수 관행이 일치한다

### Hypothesis B — 구 ⊂ v2 (기존이 일부만 잡았다) … **기각**

기존 박스가 더 **작다**는 증거가 없다. 오히려 높이 중앙 0.531 로 크고,
가이드 예시와 같은 범위를 잡고 있다. B 가 맞다면 기존 박스가 가이드 예시보다
작아야 하는데 그렇지 않다.

### Hypothesis C — 구 ≠ v2 (목적과 범위가 다르다) … **기각**

C 를 의심한 근거는 명칭의 어감 차이(`분기 접촉부` = 접촉 지점 / `케이블헤드` = 부품)였다.
그러나 가이드 자체가 두 명칭을 같은 화면에 붙여 쓰고 있어, 어감 차이는 실제 범위 차이로
이어지지 않는다. 또 v2 는 `분기 접촉부`(#13)를 PF&PT 반 전용으로 **유지**하고 있어,
같은 이름을 반에 따라 다르게 부르는 구조일 뿐이다.

## 7. migration_status 3상태 확장 — 구조 충돌 검토 (코드 미변경)

현재 `schemas/classes_v1_26.py` 의 `MIGRATION` 은
`{구id: (v2 class_name, migration_type, 근거)}` 이고 `migration_type` 은
`same / renamed / status / split` 4종이다. 이는 **기술적 변환 방식**을 뜻한다.

제안하는 `semantic_status`(`semantic_same / semantic_partial / semantic_unknown`)는
**의미 검증 상태**로, 축이 다르다. 두 필드는 서로 대체하지 않는다.

| 구 id | migration_type (기술) | semantic_status (의미) |
|---|---|---|
| 15 → 케이블헤드 | `split` | `semantic_same` (이번 결정) |
| 그 밖 25종 | same / renamed / status | **미검증** |

**충돌 없음.** 필드를 추가하는 방식이라 기존 `new_id()` 동작이 바뀌지 않는다.
다만 **이번 작업에서는 코드를 바꾸지 않았다.** 나머지 25종의 의미 검증이 안 된 상태에서
필드만 추가하면 전부 공란이 되어 오히려 오해를 부른다. 25종 검증 계획과 함께 도입한다. → NQ-9

**387개를 다시 매핑하지 않았다.** `SPLIT_BY_PANEL` 의 `P6 → cable_head` 는 그대로다.
